# Template variables (v1.2)

This document lists, per family, which context variables the packaged
templates use, and how confident we are that each name is correct.

## ⚠️ Correction from v1.1: real variable names differ from the docstring's prose

An earlier version of this document trusted the *prose description* in
`send_mail_to_student`'s docstring ("display_name: display name of a
course") and treated `display_name` as the real template variable name.
**That was wrong.** Direct inspection of edx-platform's own packaged
template for this family, plus the user's own production testing on a
live Verawood instance, confirms the actual variable is **`course_name`**,
and that a working **`password`** variable exists and is populated for
this specific family -- something the docstring's `param_dict`
description didn't surface at all (see "Why the docstring missed this"
below). All template files and fixtures in this package have been
corrected accordingly.

## Empirically confirmed: `instructor:accountcreationandenrollment`

This is the family behind the **legacy instructor-dashboard CSV batch
"auto-register and auto-enroll" feature** (Membership tab -> upload a CSV
of new accounts) -- see "The CSV auto-register/auto-enroll mechanism"
below. Confirmed two ways:

1. **Direct source inspection** of edx-platform's own packaged template:
   > https://github.com/openedx/openedx-platform/blob/master/lms/templates/instructor/edx_ace/accountcreationandenrollment/email/body.html

   That template uses, verbatim: `{{ course_name }}`, `{{ site_name }}`
   (used as a **bare domain**, directly after a literal `https://` --
   not a human-readable platform name), `{{ email_address }}`,
   `{{ password }}`, and `{{ course_url }}`.
2. **Live-instance confirmation**: the person using this plugin tested the
   CSV auto-register/auto-enroll feature extensively on a real Verawood
   instance and confirmed the email is sent with a working autogenerated
   password using this variable set.

| Variable | Confirmed use |
|---|---|
| `course_name` | Course display name, e.g. "Introduction to Testing" |
| `site_name` | **Bare domain** (e.g. `example.tld`), used directly after `https://` -- not a friendly platform name |
| `email_address` | The new account's email |
| `password` | The autogenerated plaintext password for the new account |
| `course_url` | Full URL to the course |

### Why the earlier docstring-based research missed `password`

The `lms.djangoapps.instructor.enrollment.send_mail_to_student` docstring
(the source used for the v1.1 "verified" contract) documents an 11-key
`param_dict` with no password-shaped key, and v1.1 concluded from that
that no password variable existed anywhere in this family's context. That
conclusion was too broad: it correctly described the **general-purpose**
`param_dict` shape used by `send_mail_to_student` as a function, but the
actual call path for the CSV auto-register/auto-enroll mechanism is
different from what that docstring implied:

The CSV upload is parsed by `RegisterAndEnrollStudents.post()`
(`lms/djangoapps/instructor/views/api.py`), which creates the account,
generates a password via `generate_unique_password()`, then calls
`enroll_email()` in `lms/djangoapps/instructor/enrollment.py`.
`enroll_email()` in turn calls `send_mail_to_student()` -- the same
function the docstring documents -- but the caller adds the generated
password into the `email_params` dict specifically for this
account-creation family before that call, which is not something a
docstring listing `send_mail_to_student`'s *general* parameter shape
would necessarily capture. The docstring undersold the real, per-family
contract; the packaged template (and this plugin, now) reflect what the
code and a live instance actually do.

**Lesson applied going forward in this doc:** a function-level docstring
describing a generic `param_dict` argument is a *starting point*, not the
final word on what a specific message family's template can actually
reference -- individual callers can and do add family-specific keys
before the dict reaches `ace.send()`. Where possible, this doc now
prefers direct template inspection or live-instance confirmation over
docstring prose alone.

## High-confidence by analogy: the other 6 `instructor:*` families

`allowedenroll`, `allowedunenroll`, `enrollenrolled`, `enrolledunenroll`,
`addbetatester`, `removebetatester` were **not** individually
source-inspected this session. They are treated as using `course_name`
(not `display_name`) on the strength of sharing the exact same
`param_dict`-building code path as `accountcreationandenrollment`
(all reached via `enrollment.py`'s `get_email_params()`/
`send_mail_to_student()`). They do **not** get a `password` variable --
they act on accounts that already exist (enrolling/unenrolling/beta-role
changes), so there is no new credential to report.

`check_email_templates` still labels these 6 `[verified context]`
(grounded in the same evidence chain) and `accountcreationandenrollment`
is the one with a direct source citation and live confirmation above it.
If you customize any of these 6, it's worth confirming `course_name`
against your own instance the same way, rather than assuming.

## Unverified: `support:wholecoursereset`

`lms.djangoapps.support.message_types.WholeCourseReset` is documented
(APP_LABEL=`support`, Name=`wholecoursereset`) but is built by a separate
code path (`lms.djangoapps.support`, not `enrollment.py`) that has not
been source-inspected or live-tested this session. The packaged templates
for this family use `course_name`, `course_id`, `course_url`, and
`site_name` inferred from `CourseResetAPIView`'s response shape and the
pattern of the other 7 families -- **treat these as unverified** until
checked against the real `WholeCourseReset` message-building code or a
live send. `check_email_templates` flags this family accordingly.

## Corrected: `site_url` and `user_password` still don't exist

These were checked in v1.1 and remain not part of any confirmed contract
-- nothing changed here. `site_name` (confirmed above) is the real
variable, and it's a bare domain, not a variable you'd prefix with
`https://` and a separate hostname. `password` (confirmed above, no
`user_` prefix) is the real variable for the one family that has a
password to report.

## A real bug this correction surfaced: plaintext escaping

Django's `{% blocktrans %}` HTML-escapes its variables by default, the
same as `{{ variable }}` anywhere else in a template -- including inside
a `.txt` component. A generated password containing `&`, `<`, `>`, or a
quote character would render as `Tr0ub4dor&amp;3xample` in the **plain
text** email body, which is wrong (nothing un-escapes it for the reader).
The packaged `accountcreationandenrollment/email/body.txt` wraps its
content in `{% autoescape off %}` / `{% endautoescape %}` to avoid this;
`body.html` deliberately keeps escaping on (matching upstream's own
`{% filter force_escape %}` usage), since HTML entities are the correct,
expected behavior there. If you add `password` (or any other
possibly-special-character value) to a `.txt` component in your own
customizations, wrap it the same way.

## The CSV auto-register/auto-enroll mechanism

This is the feature `instructor:accountcreationandenrollment` is sent
from: the instructor dashboard's Membership tab has a CSV-upload option
that creates new accounts and enrolls them, autogenerating a password for
each. It is **off by default** in Verawood (and, per the toggle's own
history, has been off by default since 2014), gated behind:

- **Toggle name:** `ALLOW_AUTOMATED_SIGNUPS`
- **Type:** a Django settings-based feature toggle (`DjangoSetting` in
  edx-platform's own classification -- not a `WaffleFlag`/
  `CourseWaffleFlag`, despite sometimes being referred to informally as a
  "waffle flag"; it's set in `FEATURES` the same way as many older
  edx-platform toggles, not through the Waffle admin UI)
- **Source:** `lms/djangoapps/instructor/settings/common.py`
- **Default:** `False`
- **Description (from edx-platform's own docs):** "Enable to show a
  section in the membership tab of the instructor dashboard to allow an
  upload of a CSV file that contains a list of new accounts to create
  and register for course."
- **Docs:** https://docs.openedx.org/projects/edx-platform/en/latest/references/featuretoggles.html#featuretoggle-ALLOW_AUTOMATED_SIGNUPS

A related toggle, `ENABLE_AUTOMATED_SIGNUPS_EXTRA_FIELDS` (same settings
file, also `DjangoSetting`, also default `False`), additionally accepts a
cohort name and enrollment course mode as extra CSV columns when enabled
-- it does not change which template family is used or its variables.

**Why this matters for a production instance:** if standard public
self-registration is restricted (for example, by a
`tutor-restricted-signups`-style plugin), this CSV mechanism is one of
the few ways staff can still onboard learners who can't self-register,
which is presumably why you're customizing this specific template.

To enable it in Tutor:

```bash
tutor config save --set 'LMS_FEATURES={"ALLOW_AUTOMATED_SIGNUPS": true}'
```

(merge this into your existing `LMS_FEATURES` dict rather than
overwriting it, if you have other feature flags set -- `tutor config
printvalue LMS_FEATURES` shows the current value first.)

## Tested: this plugin works with the CSV mechanism

`emailtpl_app/tests/test_overrides.py::CsvAutomatedSignupsWelcomeEmailTest`
specifically exercises this family with the confirmed variable set,
including a generated password containing a special character (`&`), and
proves:

- the rendered `body.txt` and `body.html` both contain the password
  (correctly un-escaped in `.txt`, correctly HTML-escaped in `.html`)
- the course name, email address, and a well-formed `https://<domain>`
  URL all appear
- the email sends successfully through Django's locmem backend

Run it directly with:

```bash
cd tutor_custom_emailtpl
python -m django test emailtpl_app.tests.test_overrides.CsvAutomatedSignupsWelcomeEmailTest --settings=emailtpl_app.tests.test_settings
```
